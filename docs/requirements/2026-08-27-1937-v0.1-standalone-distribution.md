# OpenScope V0.1 Standalone Distribution Requirement

> Requirement Status: implementation-ready
> Last Reviewed: 2026-08-28
> Source: cywu 2026-08-27 direct instruction; `OpenScope-项目架构.md` §15; `OpenScope-技术架构.md`
> Owner Contract: `docs/architecture/v0.1-standalone-contract.md`

## Goal

交付一个可重复启动、可查询、可证明三信号闭环的 OpenScope V0.1 standalone 发行版，证明 Spring Boot 应用通过 OpenTelemetry Java Agent 与 OTLP 进入 Collector，并在 Prometheus、Tempo、Loki 和 Grafana 中获得可验证的 Metrics、Traces 和 Logs。

V0.1 是首个可运行的 pre-release 里程碑，不等于政务/医疗生产交付版。

## Primary User Flow

1. 运维者复制 `.env.example` 并设置非默认 Grafana 管理员密码。
2. 运维者执行 `./cli/openscope start`，启动 Collector、Prometheus、Tempo、Loki 和 Grafana。
3. 开发者使用固定版本 Java Agent 启动 `springboot-simple` 示例。
4. 验收脚本生成成功与失败 HTTP 请求。
5. 运维者在 Grafana 中按 site/environment/project/namespace/service/instance 查询信号，并能在 Log 与 Trace 之间双向跳转。
6. 运维者执行 `./cli/openscope doctor` 和 `./tools/verify-v0.1.sh` 获得机器可读的通过/失败结果。

## In Scope

- 单机 Docker Compose 拓扑：Collector + Prometheus + Tempo + Loki + Grafana。
- Linux `amd64` 与 `arm64` 宿主机的同一份 Compose 声明。
- Spring Boot 4.1.1 / Java 21 示例应用，仅使用 OpenTelemetry Java Agent 2.31.1，不引入 OpenScope Starter。
- OTLP/HTTP 作为示例应用到 Collector 的默认协议。
- Traces、Metrics、Logs 全部由 Java Agent 直接以 OTLP 导出；V0.1 不采集 stdout/file 日志。
- 必需 Resource 属性：`site.id`、`project.id`、`deployment.environment.name`、`service.namespace`、`service.name`、`service.instance.id`、`service.version`。
- 基础 Overview/Service Dashboard 和 Grafana Provisioning 的 Prometheus、Tempo、Loki 数据源。
- Logs → Trace 与 Trace → Logs 双向关联。
- 最小 CLI：`start | stop | status | doctor | version`。
- 单机安全基线：只暴露 loopback Grafana 和 OTLP 入口，后端管理/查询端口不绑定宿主机。
- 每个上游组件的精确 tag、多架构 manifest digest 和来源记录。

## Out Of Scope

- Central 和 Distributed 拓扑。
- OpenScope Spring Boot Starter、autoconfigure、logback 自研模块。
- stdout/filelog、Host Metrics、JDBC/Redis/Kafka 专项 Dashboard。
- Alert、SLO、Tail Sampling、Persistent Queue。
- 离线镜像包、backup/restore/upgrade。
- TLS/mTLS、OIDC、多租户与跨网络域部署。
- Kubernetes、Helm、Mimir、Pyroscope、eBPF。
- 政务/医疗生产合规认证。

## Product Rules

1. 应用只配置 OTel/OTLP，不依赖 Prometheus、Tempo 或 Loki 私有客户端。
2. V0.1 日志路径唯一：Java Agent Logback appender instrumentation → OTLP/HTTP → Collector → Loki。
3. `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative`，V0.1 不依赖 Prometheus 的实验性 delta-to-cumulative feature flag。
4. 默认不捕获 Authorization/Cookie/Token/Body/SQL bind parameters；Collector 对已知敏感 key 再做一次删除。
5. Compose 不得使用 `latest`、浮动 major/minor tag 或未解析的 `${managed}`。
6. 任一镜像未记录 manifest digest，不得进入 Compose 首次启动。
7. `doctor` 失败时必须非零退出，不得用“完成但有警告”遮蔽确认的功能失败。
8. 验收必须查询真实后端数据，不以容器 `running/healthy` 代替信号证据。

## Roles And Permissions

- V0.1 只有本机运维者，不引入产品角色模型。
- Grafana 必须使用 `.env` 中非默认的管理员密码；密码不得提交。
- Prometheus、Tempo、Loki 与 Collector 管理端口只在 Compose 内部网络可见。

## Required Development Validation Environment

- 完整 runtime acceptance 必须通过免密 SSH 在 `root@172.16.65.59` 执行；本地 macOS 只允许做文档、静态检查或补充架构验证，不替代开发机结果。
- 远端是共享开发机，使用 `/root/workspace/openscope-v0.1`、Compose project `openscope-v01` 和独立 volume/network；下载或传输的 Java Agent、镜像归档、校验文件和其他依赖统一进入 `/root/workspace/openscope-v0.1/dependencies`，不得散落在 `/root` 或 `/root/workspace` 根层。禁止操作其他 project 的容器、镜像、volume、network 或进程。
- 默认发行版仍使用 loopback Grafana `3000`；开发机验证 profile 因现有端口冲突固定覆盖为 `127.0.0.1:13001`。OTLP 入口仍为 loopback `4317/4318`。
- 远端执行前后记录 payload Git revision/内容摘要、主机环境、端口、磁盘和非 OpenScope 容器状态；任何前置条件不满足均 fail closed。
- SSH 自动化必须验证已知 host key，不转发本地 agent，不把私钥、密码、registry token 或 Grafana 密码写入仓库/证据。

## Failure And Edge Cases

- Docker/Compose 缺失、端口冲突、磁盘不可写、密码未设置：`start` 必须拒绝启动并给出明确原因。
- 镜像 digest/tag 不一致：BOM 校验失败，不得启动。
- 任一后端不可达或 Provisioning 失败：`doctor` 非零退出。
- 应用缺失必需 Resource 属性：验收失败，不允许 Dashboard 以 `unknown_service` 通过。
- 日志中出现敏感测试值：验收失败。
- Collector 或后端重启后：V0.1 不保证重启窗口内零丢失，但服务恢复后新信号必须可再次查询。

## Acceptance Criteria

- **AC-01 BOM**：BOM 中所有容器镜像均为精确 tag + manifest digest，无 `latest`/浮动 tag。
- **AC-02 Config**：`docker compose ... config --quiet` 通过，配置文件可被各上游组件自身校验。
- **AC-03 Start/Stop**：空数据目录下 `start`、`status`、`stop` 均可重复执行，且不会创建重复资源。
- **AC-04 Network**：默认 profile 只暴露 `127.0.0.1:3000/4317/4318`；开发机 profile 只把 Grafana 改为 `127.0.0.1:13001`，后端管理端口不暴露。
- **AC-05 Trace**：成功和失败 HTTP 请求生成的 trace 可通过 Tempo API 按 `service.name` 查到，并包含完整 Resource 属性。
- **AC-06 Metrics**：Prometheus API 可查到 `target_info` 和 HTTP server 指标，且 `site_id/project_id/deployment_environment_name/service_namespace/service_name/service_instance_id` 可用于过滤。
- **AC-07 Logs**：Loki API 可查到示例日志，且 log record 包含 `trace_id`/`span_id` 与必需 Resource 属性。
- **AC-08 Correlation**：同一请求的 Loki `trace_id` 与 Tempo trace id 一致；Grafana Provisioning 同时配置 Logs → Trace 和 Trace → Logs。
- **AC-09 Redaction**：带有合成 Authorization/Cookie/token/password/body 值的测试请求后，三后端均查不到该明文测试值。
- **AC-10 Grafana**：三数据源返回成功健康状态，基础 Dashboard 已 Provisioning，六元组变量可用。
- **AC-11 Doctor**：正常栈 `doctor` 退出 0；任意停止一个后端后退出非 0 并指明失败项。
- **AC-12 Persistence**：重启 Compose 后 Grafana Provisioning 仍存在，已持久化的后端数据在它们声明的 V0.1 retention 内仍可查询。
- **AC-13 Re-run**：`./tools/verify-v0.1.sh` 连续执行两次均通过，且清理逻辑在失败时也可执行。
- **AC-14 Architecture**：`amd64` 和 `arm64` 的镜像 manifest 都存在；在指定开发机完成 `amd64` 真实运行验收，`arm64` 明确记录为 manifest-only 或附加真实运行证据。
- **AC-15 Evidence**：每项 AC 都在 `docs/testing/` 中有命令、退出码和关键响应摘要；执行、跳过、失败、人工未执行分开记录。
- **AC-16 Remote Isolation**：完整验收在 `root@172.16.65.59` 的隔离 workdir/project 中执行；前后对比证明未停止、重建、删除或改写任何非 OpenScope 资源，远端 payload 与本地待验版本一致。
