## Contract Scope

## Runtime Topology

```text
Spring Boot sample + OTel Java Agent
        | OTLP/HTTP :4318 (loopback)
        v
OpenTelemetry Collector Contrib
        | OTLP/gRPC      | OTLP/HTTP                 | OTLP/HTTP
        v                v                           v
Tempo monolithic     Prometheus native OTLP      Loki native OTLP
        \_____________________|_____________________/
                              v
                         Grafana :3000
```

- Compose 内部使用一个专用 bridge network。
- 宿主机只允许 loopback 绑定 `3000/4317/4318`。
- Prometheus `9090`、Tempo HTTP/gRPC、Loki `3100`、Collector health/debug 端口不 publish 到宿主机。
- V0.1 是 single-tenant/single-host，不宣称 HA、零丢失、跨机安全或生产合规。

### Development Validation Profile

- Required host: `root@172.16.65.59` over passwordless SSH；自动化强制 `BatchMode=yes`、`StrictHostKeyChecking=yes`、`ForwardAgent=no`。
- Remote ownership: `/root/workspace/openscope-v0.1` + Compose project `openscope-v01`；依赖统一存放 `/root/workspace/openscope-v0.1/dependencies`。所有容器、network、volume 必须带该 project ownership，脚本只能操作这一作用域。
- Host bindings: Grafana `127.0.0.1:13001`（默认 profile 的 `3000` 被现有服务占用）；OTLP `127.0.0.1:4317/4318`。
- Manual Grafana access uses an operator-created SSH tunnel to remote `127.0.0.1:13001`；验收脚本在远端直接调用 API，不依赖隧道。
- Remote validation runner 必须传输可识别的 Git revision/内容摘要、执行 preflight、运行验收、回收脱敏证据；不得从开发机上的其他 checkout 猜测待验版本。
- Shared-host invariant: 记录执行前的非 OpenScope container ID/status，执行后比较；任一非 OpenScope 容器被停止、重建或删除即验收失败。
- Disk guard: 每次 start 前检查根文件系统；低于 10 GiB 可用空间或达到 90% 使用率时阻断。禁止自动 prune、删除现有镜像或 volume。

Rules:

1. 上表是候选发行组合，不是已通过兼容性测试的 OpenScope BOM。
2. Phase 0 必须从官方 registry 解析每个 tag 的 multi-arch manifest digest，写入 `distribution/bom.yaml`，生成 SBOM/来源记录，并验证 `amd64`/`arm64` manifest；上游发布 provenance/signature 时必须一并验证，未发布时明确记录 unavailable，不得伪造。
3. Compose 只引用 `image:tag@sha256:digest`。任一 digest 缺失或不匹配都是阻断性失败。
4. 本地与指定开发机均无法直连 Docker Registry；开发机配置了镜像代理，但 Buildx 仍不能解析候选 manifest。因此本轮只冻结官方 release tag，不伪造 image digest。
5. 任一版本变更都重开 BOM 人工审批和全量 V0.1 验收，不单独升级组件。

## Signal Contracts

### Application To Collector

- 默认协议：`http/protobuf`。
- 端点：`http://127.0.0.1:4318`。
- 导出：`OTEL_TRACES_EXPORTER=otlp`、`OTEL_METRICS_EXPORTER=otlp`、`OTEL_LOGS_EXPORTER=otlp`。
- Metrics temporality：`cumulative`。
- Java Agent 与 Spring Boot Starter 不同时出现。
- Java Agent 的 `logback-appender-1.0` instrumentation 必须保持启用；Phase 2 以实际 log record 的 instrumentation scope 和后端结果证明生效，不凭默认值推断。

### Logs

V0.1 唯一日志路径：

```text
Logback event
  -> Java Agent logback appender instrumentation
  -> OTLP LogRecord
  -> Collector otlp receiver
  -> otlphttp/loki endpoint http://loki:3100/otlp
```

- 不使用 `filelog` receiver，不扫描 Docker JSON 日志或宿主机文件。
- `trace_id`/`span_id` 使用 OTLP LogRecord 标准字段，不依赖对 message 正则解析。
- Loki 在 `limits_config.otlp_config` 中显式把 `site.id/project.id/deployment.environment.name/service.namespace/service.name` 配为低基数 index labels，其余 Resource/Log 属性作为 structured metadata。
- `service.instance.id` 在 V0.1 保存为 structured metadata，避免把未来高基数模式固化进 Loki label contract。

### Metrics

- Collector exporter：`otlphttp/prometheus`。
- Base endpoint：`http://prometheus:9090/api/v1/otlp`，由 exporter 追加 `/v1/metrics`。
- Prometheus 必须启用 `--web.enable-otlp-receiver`。
- `prometheus.yml` 显式提升以下 Resource attributes：
  - `site.id`
  - `project.id`
  - `deployment.environment.name`
  - `service.namespace`
  - `service.name`
  - `service.instance.id`
  - `service.version`
- Dashboard 查询使用 Prometheus 规范化后的 label 名（如 `project_id`）。

### Traces

- Collector exporter：OTLP/gRPC 到 Compose 内部 `tempo:4317`。
- Tempo V0.1 使用 monolithic 模式和本地持久化 volume，仅适用于该 pre-release 的低流量单机验证。
- Object storage、microservices mode 与 Kafka 不进入 V0.1。

## Collector Pipeline Order

```text
receive -> memory_limiter -> resource validation/enrichment
        -> sensitive-key deletion -> batch -> export
```

- 使用 beta 级 `attributes`/`transform` 能力实现明确 key 删除，不在 V0.1 依赖 alpha 级 redaction processor 作为合规承诺。
- 处理器对 traces/metrics/logs 的稳定级别、配置和使用原因写入 BOM 元数据。
- 默认不捕获敏感 header/body/bind parameters；Collector 的第二道防线必须使用合成泄漏测试验证。

## Grafana Provisioning Contract

- 三个数据源固定 UID：`openscope-prometheus`、`openscope-tempo`、`openscope-loki`。
- Loki datasource 以 structured metadata `trace_id` 配置指向 Tempo 的 derived field。
- Tempo datasource 使用 `tracesToLogsV2`，将 `service.name` 映射到 Loki `service_name`，并启用 trace-id 过滤。
- Dashboard 六元组：`site/environment/project/namespace/service/instance`；变量值由 Prometheus `target_info` 和业务指标获得，Loki/Tempo 查询使用等价 Resource 属性。
- 任何关键 datasource/dashboard 都不得仅存在 Grafana UI 数据库中。

## Standalone Security Baseline

- Grafana 密码必须由未提交 `.env` 提供，默认密码和空密码阻断 `start`。
- 只有 loopback OTLP 入口允许宿主机应用写入；不接受 LAN/WAN 客户端。
- 后端不做宿主机端口映射，Grafana 通过 Compose 内网代理查询。
- Compose 密钥/密码文件权限和 volume 可写性由 `doctor` 检查。
- TLS/mTLS、多租户和认证反向代理是 Central/Distributed 的先决设计，不得从 V0.1 standalone 的 loopback 信任模型外推。

## Planned Repository Ownership

```text
distribution/
├── bom.yaml
└── standalone/
    ├── docker-compose.yml
    ├── .env.example
    └── config/{collector,prometheus,tempo,loki}/
grafana/
├── provisioning/{datasources,dashboards}/
└── dashboards/overview/
cli/openscope
examples/springboot-simple/
agents/java/manifest.yaml
tools/{resolve-bom,verify-v0.1}.sh
```

- `distribution/` 拥有可运行装配与版本引用。
- `grafana/` 拥有可视化资产。
- `cli/` 只调用 distribution 公开操作，不复制 BOM 或组件配置。
- V0.1 不创建假设性 Backend Adapter interface；第二个真实 Backend 出现后再设置 seam。

## Verification Boundary

V0.1 不以 mission-driver demo 作为产品验证。实施 Phase 0 必须先产生并使以下命令真实可执行：

```bash
./mvnw -q -pl examples/springboot-simple -am verify
docker compose --env-file distribution/standalone/.env.example -f distribution/standalone/docker-compose.yml config --quiet
./tools/verify-v0.1.sh
./cli/openscope doctor
./tools/verify-docs.sh
```

上述命令任一缺失、跳过关键信号或用 reconciliation 将失败降级为完成，都不得作为 V0.1 验收证据。
